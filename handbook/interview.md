## 定位与贡献范围

**VidFlow｜短视频 Feed 后端：热点计数与稳定分页**

技术栈：Go、Gin、GORM、MySQL、Redis、RabbitMQ、Vue 3、Docker Compose。

项目基于 [LeoninCS/feedsystem_video_go](https://github.com/LeoninCS/feedsystem_video_go) 二次开发。账号、视频上传、评论、关注、私信及通知提供基础业务闭环。围绕关注流正确性、点赞计数事务与恢复、对照实验完成的改造，是这次展示的主要贡献。基线 commit 为 `7c1c27d179bf22246931d249267a57df8b5cca4b`，核心改造见 `5bb2d25`。

版面较少时保留前两条，将第三条的“7,200 → 7”放入计数条目，并保留“300 req/s、两轮”的条件。数据代表特定实验中的视频行更新次数，不能改写成总数据库写入下降、接口提速或系统吞吐提高。

## 三分钟讲解

“我基于一个短视频开源项目做后端改造，主要解决两个问题：关注页刷新和翻页的正确性，以及点赞总数对视频行的频繁更新。

关注页原先按时间分页，同时间发布的作品在页边界容易漏掉，所以我增加了时间和 ID 的复合游标。刷新还会遇到旧请求晚返回的问题，后端用缓存版本校验阻止旧回填，前端用请求序号阻止旧响应覆盖新列表。组合测试中，25 条同时间作品加一条新发布作品，刷新后通过 10、10、6 三页核对完整顺序。

点赞部分，我把关系和展示计数分开。关系与计数日志先在一个事务中提交，Redis 优先提供展示总数；后台把多个增量合成一次视频更新，计数和事件完成标记一起提交。重复请求只在关系实际变化时产生事件，Redis 投影还能按事件 ID 去重，批处理失败后保留日志重试。

我跑了两种分布、三个请求率的 A/B 实验。300 req/s 热点场景两轮的视频行更新从 7,200 次降到 7 次。不过全库行写入基本持平，P95 从 2.94 ms 增至 7.91 ms，因为新版接口要确认关系和日志已经提交。这说明优化的价值是减少视频热点行更新，并在该负载下缩短积压追平时间；容量上限还需要持续压测。”

## 高频追问与代码证据

| 追问 | 回答重点 | 代码或证据 |
|---|---|---|
| 为什么不只在 Redis 查重？ | 缓存缺失不等于没有关系；数据库唯一约束决定真实关系是否发生变化 | [LikeService.change](../backend/internal/video/like_service.go) |
| 用户点两次和请求重试有什么区别？ | 前端同一个按钮发送明确目标状态，重复同一状态不重复计数 | [点赞服务](../backend/internal/video/like_service.go) |
| 为什么加恢复日志？ | 记录真实变更，使关系提交后 Redis 失败、Worker 重启仍有处理依据；代价是日志写入 | [LikeCountEvent](../backend/internal/video/like_count.go) |
| Redis 清空后如何初始化？ | 一致性快照读取数据库基线和未完成增量，并记录快照包含的事件，避免重新加一遍 | [Apply / Counts](../backend/internal/video/like_count.go) |
| 数据库已经加过，Worker 又重试怎么办？ | 数据库计数与完成标记同事务；Redis 事件去重；已完成事件不重复领取 | [Flush](../backend/internal/video/like_count.go) |
| 多 Worker 是否无限扩展？ | 当前全局刷新锁串行领取批次，支持安全协作，尚未证明横向扩展吞吐 | [Flush 锁行](../backend/internal/video/like_count.go) |
| 同时间视频如何不漏页？ | 使用确定的时间＋ID 排序边界；固定集合核对完整 ID，不只看返回条数 | [分页集成测试](../backend/internal/feed/following_pagination_test.go) |
| 请求取消后为何还要序号？ | 已送达的响应可能忽略取消，序号确保只有最新请求更新列表和 loading 状态 | [前端测试](../frontend/tests/useVideoFeed.test.mjs) |
| 全库写入也减少了吗？ | 300 req/s 热点两轮全库行写入 14,400 → 14,415；记录成本而非宣称全面提速 | [A/B 报告](../experiments/like-count/results/20261115T083209Z-ab/REPORT.md) |
| 原项目已有的功能有哪些？ | 登录、上传、评论等基础模块继承上游；重点解释自己改动的链路及验证方式 | [上游到当前差异](https://github.com/luob8110-afk/VidFlow/compare/7c1c27d179bf22246931d249267a57df8b5cca4b...4ae7f52c30b6fd0caa27cef99cf064954c91bc85) |

## 演示顺序

1. 用普通账号浏览关注页；发布一条新作品后主动刷新，查看首条与分页结束状态。
2. 对同一视频点赞，再点击同一个按钮取消，观察状态和展示计数；接口重试正确性用自动化测试说明。
3. 打开计数代码，说明关系事务、Redis 投影、批处理事务这三个边界。
4. 展示 A/B 报告的更新次数、P95/P99、全库写入与追平时间，解释收益和成本。
5. 被问到后续工作时，优先解释上传完整性、长时间计数实验及可靠通知的具体缺口和验收标准。

目前的推荐页使用最新流；关系分片是设计研究；存储实验的 DAU 是假设输入；上传完整性仍有待补项。这些内容适合作为下一步设计讨论，不应写成已经交付的项目业绩。
