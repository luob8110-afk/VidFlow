## 定位与贡献范围

**VidFlow｜短视频 Feed 后端：热点计数与稳定分页**

技术栈包括 Go、Gin、MySQL、Redis、RabbitMQ、Elasticsearch、S3 兼容对象存储、FFmpeg、Vue 3 和 Docker Compose。

项目基于 LeoninCS 的短视频项目二次开发，继承账号、初始本地上传、评论、关注、私信及通知。主要改造包括媒体资产生产、全站搜索、关注流正确性、点赞计数恢复及对照实验。点赞和关注流的对照基线为 `7c1c27d179bf22246931d249267a57df8b5cca4b`。[上游项目](https://github.com/LeoninCS/feedsystem_video_go)

## 简历条目参考

**VidFlow｜短视频 Feed 后端优化（开源二次开发）**

- 设计媒体资产状态机，支持 S3 分片直传、断点续传与整文件 SHA-256 校验。通过 RabbitMQ 调度 Go Worker 生成封面和标准 MP4，处理任务重投与租约到期恢复，发布依据 `asset_id` 校验状态和归属。[媒体链路与验证](media-pipeline.md)
- 实现 Elasticsearch 全站视频搜索，支持中文检索、结构化筛选和 PIT 游标分页。复用 MySQL 事务 Outbox，经 RabbitMQ 确认投递到独立索引队列，按视频 ID 幂等写入，支持历史回填及索引服务恢复后追平。[搜索与故障验证](video-search.md)
- 改造关注流分页与缓存：采用时间＋ID 复合游标、版本化缓存及前端请求序号，处理同时间作品漏页、主动刷新后的旧数据回填和迟到响应覆盖；通过发布—刷新—分页组合测试核对 26 条作品完整序列。
- 重构点赞计数链路：关系变更与恢复日志同事务提交，Redis Lua 实现事件去重及计数加减，Worker 按视频聚合增量并事务提交计数与完成标记，覆盖重复请求、批处理回滚及缓存丢失恢复。
- 搭建隔离 A/B 压测，完成热点/分散场景、50/150/300 req/s、24 轮共 24,000 次请求验证；在 300 req/s 热点场景，两轮视频行更新由 7,200 次降至 7 次，停写后 4.22–4.73 秒完成计数追平，记录接口延迟及日志写入成本。

版面有限时可以保留媒体、搜索和计数三条，把压测数据并入计数。注明 7,200 → 7 是 300 req/s 热点场景两轮合计的视频行更新次数。

可选存储研究条目：基于百万条关系比较 InnoDB 主键与二级索引布局，在同等“最近点赞查询”索引能力下，候选复合主键布局的样本分配空间下降约 29%；候选布局在独立实验库验证，业务表尚未迁移。依据见[关系存储实验](../experiments/edge-storage/README.md)。

## 三分钟讲解

“我基于一个短视频开源项目做二次开发，实现了从上传、转码和发布到搜索播放的链路。发布时把视频、话题与 Outbox 同事务写入 MySQL，RabbitMQ 把发布事件分别交给 Redis 时间线和搜索 Worker。搜索从 Elasticsearch 获取排序结果，再批量读取 MySQL 中的作品。测试中短暂停掉 Elasticsearch，发布和时间线继续工作，服务恢复后搜索追平积压。

关注页原先按时间分页，同时间发布的作品在页边界容易漏掉，所以我增加了时间和 ID 的复合游标。刷新还会遇到旧请求晚返回的问题，后端用缓存版本校验阻止旧回填，前端用请求序号阻止旧响应覆盖新列表。组合测试中，25 条同时间作品加一条新发布作品，刷新后通过 10、10、6 三页核对完整顺序。

点赞部分，我把关系和展示计数分开。关系与计数日志先在一个事务中提交，Redis 优先提供展示总数；后台把多个增量合成一次视频更新，计数和事件完成标记一起提交。重复请求只在关系实际变化时产生事件，Redis 投影还能按事件 ID 去重，批处理失败后保留日志重试。

我跑了两种分布、三个请求率的 A/B 实验。300 req/s 热点场景两轮的视频行更新从 7,200 次降到 7 次。不过全库行写入基本持平，P95 从 2.94 ms 增至 7.91 ms，因为新版接口要确认关系和日志已经提交。这说明优化的价值是减少视频热点行更新，并在该负载下缩短积压追平时间；容量上限还需要持续压测。”

| 为什么加恢复日志？ | 记录真实变更，使关系提交后 Redis 失败、Worker 重启仍有处理依据；代价是日志写入 | [LikeCountEvent](../backend/internal/video/like_count.go) |

| 多 Worker 是否无限扩展？ | 当前全局刷新锁串行领取批次，支持安全协作，尚未证明横向扩展吞吐 | [Flush 锁行](../backend/internal/video/like_count.go) |
| 同时间视频如何不漏页？ | 使用确定的时间＋ID 排序边界；固定集合核对完整 ID，不只看返回条数 | [分页集成测试](../backend/internal/feed/following_pagination_test.go) |

## 演示顺序

1. 发布一条带中文标题与话题的作品，用访客窗口搜索并点击播放。
2. 结合发布事务和索引代码讲清 MySQL、RabbitMQ 与 Elasticsearch 的职责，用故障记录说明停机恢复。
3. 在关注页刷新后翻页，随后对同一视频点赞再取消。解释复合游标、缓存版本与计数事务。
4. 展示 A/B 报告的热点行更新次数、P95/P99、全库写入与追平时间，解释收益和成本。

目前的推荐页使用最新流。关系分片是设计研究，存储实验的 DAU 是假设输入。媒体处理当前输出单份标准 MP4，容量结论需要持续负载实验。
