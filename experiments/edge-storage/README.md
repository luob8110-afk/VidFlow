# 一亿 DAU 的点赞和关注，关系应该怎么存？

## 从一页 Feed 倒推负载

假设一亿日活，每人每天看 10 页，每页 20 条，平均发起 10 次点赞或取消、0.2 次关注或取关，峰值取日均的 10 倍。Feed 峰值约 11.6 万页/秒，对应 231 万个点赞状态判断/秒。按用户分片后，一页的 20 个视频 ID 可以发给同一个分片批查。点赞变更峰值约 11.6 万次/秒，关注变更约 2,315 次/秒。这些是业务操作数，数据库还要承担索引更新、日志和复制。

容量单独估算。下文假定全站累计有 500 亿条有效点赞、100 亿条有效关注，取消后释放逻辑关系。活跃人数相同，产品历史和留存不同，存量可能相差数倍。以下数字采用十进制 GB/TB。

## 点赞：让“这页我赞过什么”和“我最近赞过什么”都能走索引

现有 Like 模型用自增 id 作主键，(video_id, account_id) 唯一。Feed 已有批量查询，个人点赞列表按 created_at 倒序取最近 200 条。当前模型缺少以用户开头的时间索引。扩容设计按 account_id 路由，以 (account_id, video_id) 作主键，再建 (account_id, created_at, video_id) 索引。关系本身仍然唯一，视频 ID 给时间相同的记录提供稳定的分页顺序。跨分片后先取一页视频 ID，再批量取视频详情，替换当前同库 JOIN。

这里选 MySQL 的原因是同一条关系还要保存点赞时间和支持撤销。假设给每个视频建普通定长位图，用户编号覆盖一亿个连续位置，那么一份位图需要 12.5 MB；只有 100 个赞的长尾视频也要承担这份预算。分段位图可以按需分配，但要额外支持用户维度的时间列表。高密度爆款可单独评估位图缓存，命中率和热数据分布决定收益。

| 同一百万条点赞 | InnoDB 分配空间（B/关系） | 最近点赞的索引 |
|---|---:|---|
| 现有模型，自增主键 + 唯一索引 | 98.81 | 无用户时间索引 |
| 自增主键 + 唯一索引 + 最近点赞索引 | 154.01 | 有 |
| 用户与视频组成主键 + 最近点赞索引 | 109.35 | 有 |

在同等索引能力下，省去独立的唯一索引后，每条少 44.66 B，降幅 **29.0%**。相对现有精简表，增加时间查询能力需要多付约 10.53 B/条。本次 EXPLAIN 中，按用户批查视频命中 PRIMARY，最近点赞命中 recent 并反向扫描。InnoDB 的二级索引携带主键列，所以更宽的主键也有成本，是否划算要计入每个索引。[MySQL 索引结构说明](https://dev.mysql.com/doc/refman/8.0/en/innodb-index-types.html)

**热点和重试。** 当前 worker 分别写关系、视频计数和热度。若关系插入成功后计数失败，重投会因重复关系跳过计数；爆款还会让大量不同用户争用同一视频行。扩容设计在关系所属分片的同一事务内提交状态变更和 outbox 事件，仅对实际发生的变化产生带唯一 ID 的增减事件。消费者把事件去重和计数更新放在同一事务中，按视频和用户哈希桶累计，批量汇总展示。个人点赞状态可以在提交后读主分片，展示计数允许短暂延迟。容量测试需覆盖爆款集中写、重复投递和计数积压后的追平。

## 关注：把两个方向的读取成本都算进去

现有 Social 模型有自增主键、关系对唯一索引、关注者和被关注者两个单列索引。两边列表各取最多 200 条，再查账号资料。单库候选设计以 (follower_id, vlogger_id) 作主键，反向索引用 (vlogger_id, follower_id)。判断关注、列关注、列粉丝都能通过索引取 ID；分页用上一条对端 ID 续读。这个顺序支持按 ID 翻页，若产品要求按关注时间倒序，两边都要增加时间字段并重新测量。

| 同一百万条关注 | B/关系，已合计两个方向 | 读写取舍 |
|---|---:|---|
| 现有四棵索引树 | 157.68 | 两个方向都在一张表 |
| 复合主键 + 反向索引 | 90.41 | 同库事务维护两边，省 42.7% |
| 正向表 + 反向表，各用一棵聚簇索引 | 108.30 | 可分别按关注者、作者路由 |

按关注者分库后，单库反向索引只能找到本分库的粉丝。独立反向表每条关系多花约 17.89 B，却能让一次普通作者的粉丝翻页只访问作者所在分片。对超大作者，再按粉丝 ID 哈希拆桶，每桶带游标读取，归并后取一页。桶数越多，读取扇出越大，应按作者写入峰值决定。正向表作为事实源，与变更事件同事务提交；反向投影按关系版本处理重投和乱序，取关保留删除版本直到越过重放窗口，定期对账。这部分事件、版本及删除记录需要另计。关注 Feed 现有跨表子查询也需改为先取关注作者 ID，再向内容服务取候选视频。

## 换算成预算

假定一主两副本，三份同规格存储。按上述样本的每条分配空间线性外推：

| 数据与布局 | 三份基础表及索引容量 | 对比 |
|---|---:|---|
| 500 亿点赞，自增主键且补齐时间索引 → 复合主键 | 23.10 → 16.40 TB | 省 6.70 TB |
| 100 亿关注，现有布局 → 单库双索引 | 4.73 → 2.71 TB | 省 2.02 TB |
| 100 亿关注，现有布局 → 可独立路由的正反表 | 4.73 → 3.25 TB | 省 1.48 TB，另计投影维护 |

采用点赞复合主键和关注正反表，样本外推约少 **8.18 TB**。以可按量缩减的磁盘单价 P 元/GB·月计算，基础空间差额约 **8,180 × P 元/月**。两边相同的副本系数已经计入。整机采购按实例档位计费，只有释放出的空间允许降档或减少实例才有现金节省。估算排除了备份、binlog、outbox、投影版本、空闲余量、CPU 和 IOPS；关注基线也没有独立路由能力。这张表衡量的是关系布局的空间代价。

分片数还受吞吐约束。以点赞为例，若压测证实一个主分片在目标 P99 和既定读写混合下能承受每秒 4,000 次关系变更，按 60% 使用率，写峰值至少需要 49 个主分片。实际选型还要取批读吞吐、单片可用容量和故障转移约束中更高的值。4,000 是演算输入。本次验证覆盖存储和访问路径，尚未测得集群吞吐或延迟。

## 复现实验

使用隔离的 MySQL 8.0.46、16 KiB 页，在一个空数据库执行同目录的 [edge-storage.sql](edge-storage.sql)。脚本按相同的事件顺序向各候选结构写入 100 万条关系，保留 64 位 ID，点赞时间精度为毫秒。样本含一万个用户，每人一百条不同关系。执行 ANALYZE TABLE 后取 DATA_LENGTH + INDEX_LENGTH 除以关系数，包含索引页的空闲空间。两个方向独立建表时合计两张表的占用。脚本末段还可查看三类读取的执行计划。

样本均匀、只插入，便于复现。上线前应使用真实长尾分布和反复点赞、取关的轨迹，测量稳定期的页占用、列表 P99、每片峰值 QPS 及反向投影延迟。当前服务仍使用原有表结构，以上候选结构在独立实验库验证。
