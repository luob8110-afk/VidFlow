# 2.2 查询索引短测对照

2026-11-14 完成。固定 1,000 名作者、100,000 条主作品，每组 1,000 名读者，其中相同的 100 名活跃读者承担负载。关注数为 20、100、200，每秒 20 次主请求和一次发布，发布后立即刷新检查。

## 方案与筛选

A 使用当前正确版本与原有索引。最初仅新增时间、ID、作者联合索引，SQL 抽样仍然选择作者索引并排序。因此正式 B 使用新索引加 FORCE INDEX 指定访问路线，业务改动位于关注查询的 Table 表达式中。

抽样中，关注 200 人的首页从读取约 20,000 条候选并排序，变为沿时间索引扫描 104 条后得到一页及下一条。关注 100 人的对应抽样从约 10,000 条变为 140 条。初筛同时核对三位读者各三页的 ID 序列。

## 短测协议

每种关注数和场景执行 A1、B1、B2、A2。场景为主动刷新和连续三页，每轮 30 秒、600 次主请求。共 24 轮，正式负载计划 12 分钟，主请求 14,400 次、发布 720 次、发布后刷新检查 720 次，正式测量请求共 15,840 次。

每轮清理上一轮发布作品、重置独立 Redis 并通过 API 预热。资源、容器环境变量、MySQL 参数、请求轨迹、数据规模保持一致，实验变量为查询访问路线对应的镜像、关注查询源码和新增索引。每轮前后核验各自环境，跨方案核验其他字段一致。

P95 表值为两轮 P95 的中位数。均摊读取量为整个测量窗口的 InnoDB 读取行数除以主请求与刷新探针请求数，包含固定的单作者探针和后台事件处理。发布 P95 每轮只有 30 个样本，需要结合原始记录解释。

## 退化与采用判断

B 中仅关注一名作者的刷新探针明显变慢，诊断计划与每组探针分位数保存在归档。这部分额外扫描也进入均摊读取量，因此关注 20 人的整个混合负载读取量增加，尽管主请求耗时有所降低。

本轮确认 B 对 20～200 人的主请求有收益，同时确认统一强制该索引会使低关注场景退化。候选方案适合进一步验证查询路线选择规则，默认实现保留 A。由于候选存在已复现的退化，本轮以短测形成取舍结论，长测确认安排在路线选择规则验证通过之后。

## 正确性、运行异常与交付

24 个正式轮次全部通过页内去重、关注集合、排序、下一页游标、三页周期跨页去重、发布后刷新与固定 25 条同时间作品完整翻页检查。启动试跑中 API 先于消息队列就绪，Outbox 未排空，该尝试保留在 pilot 并重跑。切换方案时的旧 HTTP 连接也曾导致预热断开，测试端改为每轮重建连接后继续执行。

源码候选在独立镜像中验证，candidate.patch 与 candidate.sql 一起交付。测试结束后恢复独立环境至 A，清理测量新增作品，保留固定样本，并停止压测容器。2.1 长测与本轮短测各自保留，方案取舍使用本轮 A/B 结果。
