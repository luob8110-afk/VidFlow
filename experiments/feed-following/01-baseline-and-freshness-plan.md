## 第一项问题的执行方案

### 要交付的行为

作者收到发布成功响应后，粉丝再主动刷新关注页，服务端查询数据库中的最新关注作品。符合关注关系、位于本次首页范围内的新作品应出现在返回结果中。网页收到成功结果后重置到最新一页。

这里以主动刷新作为触发点。普通重复读取允许使用短期缓存，初始缓存期限建议为 30 秒。这个期限以及下面的性能门槛都是待复测的方案参数。

### 根因

当前关注页按读者、页大小和翻页时间保存整个响应，缓存期限为 24 小时。发布流程将事件交给后台更新全局时间线，关注页却直接从数据库查询并维护自己的缓存，两条路径之间没有对应的缓存更新。

网页还有一份已加载的列表。首页关注标签在列表已有内容时直接复用，因此只改服务端缓存还无法完成用户看到新作品的流程。

### 建议采用的做法

1. **区分主动刷新和加载更多。** 给现有关注流请求增加可选的 `refresh` 字段，默认 false。首页请求 `latest_time=0, refresh=true` 表达主动刷新，查询 MySQL 主库并返回新结果。带历史游标又要求刷新的请求返回参数错误，避免混淆语义。
2. **保留普通请求的短期缓存。** 首次缓存期限取 30 秒，并使用关注流专用配置，避免改变其他 Feed。期限从生成这份结果的数据库查询开始时计算，查询期间用掉的时间从期限中扣除，超期结果不再写入缓存。
3. **让旧查询无法覆盖刷新结果。** 每位读者维护一个随机生成的缓存版本。刷新前更换版本，查询开始时记住自己的版本。准备写缓存时，只有该版本仍是当前版本才允许写入。读缓存时同样核对版本。随机标识避免缓存版本过期后重新从零计数、误用旧结果。
4. **接通网页的刷新操作。** 首页关注标签增加明确的刷新入口，首次进入时发起刷新，已有 Feed 页面中的刷新按钮也传入 `refresh=true`。刷新成功后替换列表并重置翻页位置。取消旧分页请求，并用请求编号忽略迟到响应，避免新列表被旧分页内容改写。请求失败时保留已有列表，显示本次刷新失败。
5. **复用关注和取关的失效入口。** 数据库确认关系变更后，更换该读者的同一缓存版本，避免旧关注集合的慢查询重新写回。缓存使用新的命名空间，旧版 24 小时缓存自然过期，新实现从新空间读取。

例如，一个旧请求先读到了旧作品。作者随后发布，粉丝刷新并得到新作品。最后旧请求才结束。缓存版本检查会阻止最后一步写入，因此新结果能继续保留。

版本检查和缓存写入需要在 Redis 中原子完成，否则二者之间仍可能插入一次刷新。现有 Redis 客户端可复用，补充一个短小的条件写入脚本。Redis 官方说明了脚本的原子执行语义。[Redis Lua 文档](https://redis.io/docs/latest/develop/programmability/eval-intro/)

### 为什么选择这套方案

主动刷新需要得到当前数据，直接查询已经提交作品的主库，能够给出明确的结果。普通请求仍可复用短期缓存。版本校验处理慢查询回写造成的新旧覆盖问题。

如果只缩短缓存期限，刷新仍可能读到过期前的旧结果。如果在每次发布时逐个清理所有粉丝缓存，发布成本会随粉丝数增长，并提前引入待比较的分发策略。当前方案把额外工作放在发起刷新的读者身上，先建立功能正确的读时查询版本，供后续分发方案公平对比。

代价是主动刷新会访问数据库。第一次试跑已经说明未缓存的查询在较高负载下会积压，因此必须复测混合负载，记录主动刷新占比、数据库读取量和错误率。

### 异常处理与修改范围

- Redis 读写或版本更新失败时，主动刷新继续查询数据库，跳过本次缓存回写，并记录缓存故障。数据库查询失败或超时时，返回明确失败结果。
- Redis 的每次操作使用自己的短超时。数据库查询采用单独的超时预算，避免沿用现有覆盖数据库等待期间的 50 ms 缓存上下文。
- 缓存未命中的普通请求继续使用现有合并重复查询或锁的思路。等待必须尊重请求取消，等待结束后按已定义的查询预算处理。
- 计划涉及关注流请求结构、处理器和服务，Redis 条件写入能力，关注/取关缓存失效入口，以及两个网页调用入口。
- 作品权限在 C 阶段由读取入口核验，关注页的缓存新鲜度是独立的行为约束。

### 验收安排

| 检查 | 操作 | 通过条件 |
|---|---|---|
| 已访问过的粉丝 | 预热首页，作者发布，粉丝主动刷新 | 成功响应包含位于首页范围内的新作品 |
| 首次访问的粉丝 | 作者发布，另一名粉丝首次进入关注页 | 得到相同规则下的最新结果 |
| 多入口 | 首页关注标签、Feed 页刷新按钮和直接 API 请求分别操作 | 刷新语义一致 |
| 旧查询晚返回 | 暂停旧查询，发布并完成刷新，再放行旧查询 | 之后普通读取仍保留新结果 |
| 多服务实例 | 旧请求和刷新分别落到不同 API 实例 | Redis 版本检查仍阻止旧结果回写 |
| 旧网页请求晚返回 | 刷新前发出分页，刷新后让分页响应到达 | 新列表不会混入旧分页结果 |
| 关注关系改变 | 关注或取关后，再让旧查询完成 | 新请求使用当前关系，旧查询不会恢复旧缓存 |
| 缓存故障 | Redis 不可用时发布并刷新 | 数据库正常且查询成功时，新作品可见 |
| 查询失败 | 让数据库查询超时或失败 | 页面明确提示刷新失败，已有内容保留 |
| 普通缓存到期 | 不传刷新标志，跨过缓存期限继续读取 | 超期结果不被继续使用 |

性能复测沿用第一次的三组关注关系，分别测全部缓存命中、全部主动刷新、以及普通读取与刷新混合。每轮至少 120 秒，覆盖 30 秒缓存到期后的行为，记录 HTTP 延迟和客户端调度等待。

初始验收目标为正常依赖下每秒 20 次主动刷新时错误率为 0、HTTP P95 不超过 200 ms。这个门槛用于第一项功能验收，仍需记录真实结果及数据库代价。原有每秒 300 次缓存命中场景也应复测，并单独说明增加版本检查带来的变化。

### 确认后的实施顺序

先实现后端刷新语义与缓存版本检查，再接通网页入口，然后验证正常流程、并发晚返回和故障场景，最后按同一数据复测并与第一次基线对照。

第一项完成后回到项目目标，进入同秒作品分页完整性改造，再跑通作品转私密后的访问撤销链路。关注流的分发方式在这些行为可验证之后继续比较。

## 阶段 1 实现与验收

本轮主线为刷新后及时看到新作品、连续翻页完整取得作品。阶段 1 完成刷新能力，阶段 2 处理分页完整性，阶段 3 验收二者组合使用的流程。

用户确认通过点击主页上方的“推荐”和“关注”刷新，重复点击当前标签同样发起首页请求。实际入口为 `HomeView.vue` 和 `useVideoFeed.ts`，`/feed` 当前重定向到主页，原方案提及的 `FeedView.vue` 未接入当前路由。

实现包含以下行为。

- 关注首页携带 `refresh=true` 读取主库，刷新成功后替换列表、更新游标并回到第一条。普通关注页缓存初始期限为 30 秒，查询耗时从缓存期限中扣除，数据库读取采用 2 秒预算，Redis 操作分别采用 50 毫秒预算。
- 每位读者使用随机缓存版本，刷新、关注、取关会更换版本。Redis 脚本原子校验版本并读取或写入页面缓存。新版键空间隔离旧版 24 小时缓存。
- 同一实例中的同版本普通缓存未命中请求使用 singleflight 合并。主动刷新独立查询，等待共享查询的请求可以取消，共享数据库读取受独立超时约束。
- 前端每个标签维护请求编号与 AbortController，只有当前编号可以修改列表、游标、错误和加载状态。切换标签后的滚动、播放处理也校验最新操作，刷新失败保留已有内容并显示错误。
