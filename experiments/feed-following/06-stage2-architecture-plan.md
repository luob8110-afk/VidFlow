# 第二阶段补齐计划

制定日期为 2026-11-15。本文件明确后续目标与验收标准，本次仅制定计划，不执行架构改造或压测。

## 总目标与现状

第二阶段要交付可验证的关注流架构。正常访问时减少重复工作，过载和依赖故障时控制资源占用，压力解除后能够恢复。在相同新鲜度要求下，比较查询、缓存与分发的读取成本、发布写入放大和积压恢复。

已完成两项工作。

| 阶段 | 已有交付 | 结论与边界 |
|---|---|---|
| 2.1 正确版本基线 | 固定数据与资源下的普通读取、主动刷新、混合读取和三页浏览记录 | 建立对照，尚未证明过载安全和最大稳定容量 |
| 2.2 查询索引对照 | A/B 短测、执行计划、候选源码和 SQL | B 有局部收益和单作者退化，默认保留 A，人数切换规则暂不展开 |

当前已有约 30 秒的关注页缓存、随机版本与原子读写校验、同实例同版本同页普通请求的 singleflight，以及发布事务、Outbox 和全局时间线消费者。主动刷新独立回源。关注流尚无统一回源准入，数据库连接池未显式设置最大连接数。

## 不变的行为与范围

- 发布成功后主动刷新，成功响应必须包含符合关注集合且处于首页范围内的新作品。过载时允许明确失败，网页保留原列表。不得把旧缓存作为刷新成功的结果。
- 保留时间与 ID 复合游标。固定作品集、固定关注关系下，跨页无遗漏、无重复。并发发布和关系变更沿用已有契约，不另行承诺整个浏览过程的静态快照。
- 所有关注流业务数据库回源都受保护，包括主动刷新、普通缓存未命中和 Redis 故障回源。鉴权等入口依赖另行核对，不能把业务查询受控描述为所有数据库访问均已隔离。
- 沿用现有 Go 服务、Redis、MySQL、RabbitMQ 和 Outbox。扩展保护与读取路径，暂不拆分微服务或引入新的基础设施。
- 原主线第三阶段的作品可见性另行实施，本阶段不增加权限产品能力。
- 关注数仍以 20、100、200 为主组，保留 0/1 人正确性与退化样本。未来 1 万、10 万关注只作设计推演。

## 2.3 记录回源路径，确定容量预算

### 目标

能够说明每类请求走到哪里、为何访问数据库，以及后续保护机制限制什么资源。

### 补齐内容

1. 画出实际请求路径，列出缓存命中、未命中、主动刷新、Redis 故障和共享查询等待等分支。
2. 增加低基数计数与耗时记录。区分请求类型、缓存结果、实际回源次数、共享查询执行次数与等待人数。预留准入、排队、拒绝、取消等指标口径。
3. 记录回源在途数及峰值、等待人数及峰值、数据库连接池使用量和等待时间。应用关注流查询计数与全库读取行数分别统计，单作者探针与主负载分别汇总。
4. 制定可配置的入口、回源并发、等待人数、等待时间、连接池和后台处理预算。说明哪些按实例生效、哪些按整个部署生效，以及对发布等业务的资源分配方式。
5. 复用 2.1/2.2 结果给出首轮保守配置，标注测量依据和待校准参数，不把数据库 max_connections 直接当作安全查询并发数。

### 交付与验收

- 一份请求链路和容量配置表，各参数有作用范围、单位、默认值、上限和配置来源。
- 小批固定请求能核对缓存命中与真实回源计数，统计路径清楚。请求计数与 singleflight 执行计数分别解释，不假设两者一一对应。
- 指标标签不包含用户 ID、游标等无限增长字段，日志不暴露鉴权凭据。
- 正常流程回归通过，延迟与额外开销有短测记录。

### 阶段结束回顾

确认已经具备解释后续结果的证据，随后进入保护实施。本阶段不追求完整监控平台或新的极限容量结论。

## 2.4 实现统一回源准入与过载保护

### 目标

请求增加时，正在执行的回源、等待队列和等待时间始终有界。Redis 失效时保护仍有效，拒绝能够尽早发生。

### 补齐内容

1. 在进入昂贵工作之前限制在途请求，接入账号刷新频率限制。不同用户的合法请求仍需共同接受服务容量限制。
2. 为关注流业务数据库回源设置统一准入，覆盖三类回源原因。普通缓存命中继续直接返回，普通相同请求先合并，真正执行的共享查询再申请回源额度。
3. 设置并发上限、有限等待队列和等待期限。取消或超时的等待者退出，不留下后台排队任务；执行完成或失败都释放额度。
4. 主动刷新在获得准入后再旋转缓存版本，避免被拒绝的刷新无谓地使当前缓存失效。刷新成功的新鲜度承诺保持不变。
5. 配置数据库最大连接数等池参数，结合应用侧预算为其他业务保留余量。说明后台任务和鉴权访问的边界，避免仅设置一个共享连接上限就宣称完成业务隔离。
6. 区分账号限频、服务过载、依赖失败与请求取消。返回可识别结果，前端保留内容；检查前端、代理和服务端重试，不立即自动重复失败请求。
7. Redis 不可用时，本地并发和排队限制继续生效。不能依赖唯一的 Redis 限流器来保护 Redis 故障回源。

### 交付与验收

- 各回源分支的实际在途峰值不超过配置上限，等待峰值不超过队列上限。
- 超额请求快速结束或在配置的等待期限内结束，允许合理调度误差并记录该误差。
- 失败、取消和超时后额度全部归还，压力解除后无需重启即可接受正常请求。
- 拒绝的刷新不旋转缓存版本；成功的刷新、同秒分页和迟到结果防覆盖回归通过。
- Redis 故障和数据库变慢时，上述边界仍成立。持续观察发布探针，报告其延迟与错误，不以关注流拒绝率降低代替其他业务健康。
- 短时超过容量时区分主动拒绝和非预期错误，不能把全部非 200 响应统一算为架构失败，也不能把拒绝请求排除出整体结果。

### 阶段结束回顾

确认系统已能守住资源边界，再讨论如何提高有效吞吐。不继续扩展成通用限流框架，按当前关注流需求完成实现。

## 2.5 比较缓存与分发，减少数据库工作

### 目标

在 2.4 的保护边界内，用相同新鲜度要求比较减少回源的办法，补齐原定第二阶段的策略对照。

### 补齐内容

1. 根据 2.3 的真实路径占比选择一个缓存候选、一个分发候选。先说明它们能节省哪类请求的工作，尤其核对当前首次进入和点击关注都会主动刷新的行为。
2. 缓存候选明确复用范围、失效与并发回写规则。不能仅延长缓存 TTL 后，把主动刷新继续直查数据库的场景描述为已经受益。
3. 分发候选先做最小可测实现，定义读时准备与发布时准备的边界，明确活跃读者、作者更新频率和写入放大的取舍。不要先实现完整大规模粉丝分发平台。
4. 先验证新鲜度再测性能。异步列表尚未覆盖应当可见的作品时，需要有可证明的判断及受控补查或明确失败机制，仅有消息队列和短 TTL 不足以满足主动刷新承诺。
5. 同时记录读取成本、缓存命中、有效吞吐、发布响应、每次发布的数据库与 Redis 写入、事件积压、重复处理和恢复代价。
6. 候选在独立环境验证，未通过者保留失败原因和证据，默认实现不提前切换。

### 交付与验收

- 当前方案、一个缓存候选、一个分发候选的对照记录。候选先通过行为门槛；不满足者标明淘汰原因，不继续投入长测。
- 通过行为门槛的候选在同一数据、资源、保护预算、请求轨迹和新鲜度下比较。若确需变更预算，另列实验，不混入算法收益。
- 每个候选说明收益适用范围、读取节省、发布写入放大和故障行为。采用或保留现状都必须有证据。
- 分发候选至少验证固定事件集的重复投递、短时消费暂停与恢复。只有实际完成的范围可以宣称已具备。

### 阶段结束回顾

选定后续使用的方案或明确保留现状。查询索引候选沿用 2.2 结论，只有对整体目标有明确帮助才重新打开人数切换议题。

## 2.6 验证扩容、故障与恢复，完成第二阶段验收

### 目标

证明保护和选定方案在容量内、超载时以及恢复后都有明确行为，并交付可复现结果与运行配置。

### 补齐内容

1. 逐步增加请求速率，区分输入流量、成功吞吐、主动拒绝和非预期失败。找到当前测试环境中的可持续区间，不推算无限容量。
2. 执行短时突发、持续超载、Redis 失效、数据库变慢及依赖恢复。选择能触发保护边界的负载，不围绕固定的 1000 用户数设计参数。
3. 对选定方案执行单 API 与双 API 对照，保持数据库资源和关注流总回源预算相同。核对各实例额度之和，避免扩容等于扩大数据库压力。
4. 队列或后台任务暂停后，记录积压量、处理速度、对正常读写的影响和清空时间，验证恢复过程不会触发第二次过载。
5. 冻结最终配置、源码与镜像摘要、脚本及结果。整理部署前需要校准的参数和回退方式。

### 交付与验收

- 各故障窗口都能核对执行与等待上限，资源没有随请求积压无界增长，客户端重试没有放大输入。
- 单实例与多实例都遵守部署总预算。扩容是否提高吞吐如实报告，下游受限时不以吞吐必须翻倍为验收要求。
- 压力和故障解除后，无需人工重启即可恢复正常处理，连接、准入额度及队列回到稳定状态。恢复观察期限在实验前写入协议。
- 给出容量内成功请求 P95/P99、全体请求结果、拒绝耗时、恢复时间和发布探针结果。200 ms 继续作为已有正常基线场景的 P95 门槛，不作为无限输入下全成功的承诺。
- 所有成功请求维持新鲜度与分页契约，最终形成第二阶段结论，进入作品可见性阶段。

## 控制实验成本与环境一致性

- 沿用 1,000 名作者、100,000 条主作品与固定随机种子。主组为 20、100、200，已有 0/1 人样本保留。不通过同时改作品总量、活跃用户数和关注集合来制造收益。
- 初筛使用少量请求、确定性测试和短窗口，只有候选有效且解释清楚后才做确认测试。一般短测为 15～30 秒；缓存过期用可控时钟或单独覆盖真实 TTL 的窗口验证，不能用短于 TTL 的窗口证明过期后的稳定性。
- 只对最终关键场景做 60～120 秒确认，不默认重复之前全部长测矩阵。持续时间、重复次数和停止条件在执行前确定。
- 比较分组保持环境变量、资源限制、数据库参数、数据和轨迹一致，只允许该组声明的实验变量变化。保护参数也是环境的一部分，需要纳入摘要核验。
- 故障与过载测试均在独立环境执行。负载器设置请求数、在途数和总时长上限，发现客户端调度中断时停止，避免恢复后补发造成未声明的突发。
- 主负载与单作者探针分别报告，然后汇总整体成本。包含发布和后台任务的数据库全局计数明确标注，不直接当作某类 SQL 的扫描行数。

## 执行与汇报约定

按 2.3、2.4、2.5、2.6 依次推进，每阶段完成后单独汇报目标完成情况、运行结果、限制和主线回顾，再判断是否进入下一阶段。执行期间持续报告正在验证的内容、关键发现、异常及处理；不只展示最终压测数字。

2.3 的下一项是读取路径、统计口径和容量配置，不直接开始大规模压力测试。当前文档的制定不代表已开始 2.3 实施。
